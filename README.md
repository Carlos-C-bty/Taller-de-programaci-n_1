# University Enrollment Management System

## Project Description

This project is a Java-based University Enrollment Management System developed as part of the Programming Workshop 2026.

The main purpose of the project is to demonstrate the application of Object-Oriented Programming principles through a simple university domain. The system models people involved in the academic environment, including students and professors, as well as the enrollment process.

The project follows a standard Maven-style directory structure and separates the different responsibilities of the application into domain, application, and infrastructure packages.

The domain package contains the main entities of the system, including Person, Student, Professor, and Enrollment. These classes represent the main concepts of the selected problem domain and demonstrate the use of Object-Oriented Programming principles.

The application package contains services responsible for coordinating application operations, while the infrastructure package contains components related to external resources and technical implementations.

The project was developed using Java and GitHub as the version control platform. GitHub Copilot was also used as an assistance tool during the development of the Object-Oriented Programming classes. The suggestions generated by Copilot were reviewed critically and modified when necessary.

The project demonstrates four important Object-Oriented Programming principles: encapsulation, abstraction, inheritance, and polymorphism. These principles help organize the code, reduce duplication, improve maintainability, and represent relationships between entities in the university domain.

The development process also follows Git best practices, including the use of commits following the Conventional Commits specification.

# Object-Oriented Programming

The project demonstrates four of the main principles of Object-Oriented Programming:

- Encapsulation
- Abstraction
- Inheritance
- Polymorphism

## Encapsulation

Encapsulation is implemented through private attributes and public methods that control access to the internal state of the objects.

For example, the Student class contains private attributes such as the student code and academic program. These attributes cannot be accessed directly from outside the class.

    private final String studentCode;
    private String program;

The class provides methods such as getters and setters to control access to this information.

Validation is also implemented inside these methods to prevent invalid values from being assigned to the object.

---

## Abstraction

Abstraction is demonstrated through the Person class.

The class is declared as abstract:

    public abstract class Person

Person contains information and behavior that are common to different types of people in the university system.

It also defines an abstract method:

    public abstract String getRole();

This method forces subclasses to provide their own implementation of the person's role.

---

## Inheritance

Inheritance is demonstrated by the Student and Professor classes.

Both classes inherit from Person:

    public class Student extends Person

and:

    public class Professor extends Person

This allows both classes to reuse common attributes and behavior defined in the Person class while maintaining their own specific characteristics.

The inheritance relationship can be represented as:

    Person
    /    \
   /      \
Student  Professor

---

## Polymorphism

Polymorphism is demonstrated through the getRole() method.

The Person class defines the abstract method:

    public abstract String getRole();

The Student class provides its own implementation:

    @Override
    public String getRole() {
        return "Student";
    }

The Professor class provides a different implementation:

    @Override
    public String getRole() {
        return "Professor";
    }

Therefore, the same method can produce different behavior depending on the object that implements it.

For example:

    Student   -> getRole() -> "Student"
    Professor -> getRole() -> "Professor"

# Domain Classes

## Person

Person is an abstract class that represents the common characteristics of people in the university system.

Its main responsibilities are:

- Store the person's identification.
- Store the person's name.
- Store the person's email.
- Define the common behavior of people.
- Define the abstract getRole() method.

---

## Student

Student represents a university student.

It inherits from Person and contains additional information such as:

- Student code.
- Academic program.

The class validates the student code and academic program to prevent invalid data.

---

## Professor

Professor represents a university professor.

It inherits from Person and contains additional information such as:

- Employee code.
- Department.

The class also validates the information received during object creation and modification.

---

## Enrollment

Enrollment represents the enrollment of a student in a course.

It contains:

- The enrolled student.
- The course name.
- The student's grade.

The class also validates grades to guarantee that they remain between 0 and 5.

The method hasPassed() determines whether the student has passed the course.

# GitHub Copilot Usage

GitHub Copilot was used as an assistance tool during the development of the Object-Oriented Programming classes.

Copilot was used to generate initial code suggestions for the domain classes. These suggestions were not accepted blindly. Each generated solution was reviewed and modified according to the requirements of the project.

The main classes developed with assistance from Copilot were:

- Person.java
- Student.java
- Professor.java
- Enrollment.java

The generated code was reviewed to verify correctness, maintainability, validation, and compliance with Object-Oriented Programming principles.

# Critical Evaluation of Copilot Suggestions

## Person.java

Copilot suggested using an abstract Person class containing the common information and behavior of people in the university system.

The suggestion was appropriate because students and professors share common characteristics.

The implementation was modified by adding validation for the name and email fields. The identification field was also defined as final because it should not be unnecessarily modified after object creation.

---

## Student.java

Copilot suggested implementing Student as a subclass of Person.

This suggestion was correct because a student is a specialized type of person within the selected domain.

The implementation was modified by adding validation for the student code and academic program.

The getRole() method was also implemented to demonstrate polymorphism.

---

## Professor.java

Copilot suggested implementing Professor as another subclass of Person.

This was appropriate because professors share common characteristics with students but also have specific attributes such as an employee code and department.

Validation was added to ensure that these attributes cannot contain empty values.

The getRole() method was implemented to provide a specific behavior for professors.

---

## Enrollment.java

Copilot suggested creating an Enrollment class to represent the relationship between a student and a course.

This suggestion was appropriate for the selected domain.

The implementation was modified by adding validation for the student's grade. The grade must remain between 0 and 5.

The hasPassed() method was also added to represent the business rule used to determine whether the student passed the course.

---

## General Evaluation

GitHub Copilot was useful for generating an initial structure for the domain classes. However, the suggestions were reviewed manually instead of being accepted without modification.

The generated code was improved by adding validation, applying encapsulation, defining appropriate inheritance relationships, and implementing polymorphic behavior.

This process demonstrated that Copilot can accelerate development, but the programmer is still responsible for reviewing, understanding, and validating the generated code.

# GitHub Copilot Code Review

## Reviewed Class

The class selected for the Copilot review was:

    Student.java

The `/review` command was used to analyze the implementation of the class.

## Copilot Report

GitHub Copilot identified one clear issue in the Student.java class.

The report indicated that there was a syntax error in the constructor signature. Specifically, the parameter list contained an unnecessary `S` after the `name` parameter:

    String name, S

Copilot indicated that this syntax error would prevent the class from compiling correctly.

Copilot also identified several positive aspects of the implementation:

- The Student class correctly extends Person.
- The fields are private and accessed through getters.
- The getRole() method is implemented consistently with the pattern used by Professor.

Copilot concluded that the class was structurally sound apart from the constructor typo.

---

## What Did Copilot Identify?

Copilot identified a syntax error in the constructor of Student.java.

The problem was caused by an extra `S` in the constructor parameter list. This was a real error because Java would not be able to compile the class correctly while the invalid syntax was present.

Copilot also confirmed that the inheritance relationship with Person was correct, that the class used private fields, and that the getRole() method followed the expected implementation pattern.

---

## Was Copilot Correct?

Yes, Copilot was correct.

The extra `S` in the constructor was a genuine syntax error and needed to be removed. The compiler would not accept the constructor while this character was present in the parameter list.

The other observations were also correct. Student extends Person, its fields are private, and getRole() correctly overrides the abstract method inherited from Person.

The review was useful because it detected a small syntax error that could prevent the entire class from compiling.

---

## What Was Modified?

The constructor of Student.java was corrected by removing the extra `S` from the parameter list.

The incorrect version was:

    String name, S

It was changed to:

    String name,

No other structural changes were necessary because Copilot confirmed that the inheritance, encapsulation, and getRole() implementation were correct.

After making the correction, the class was saved and the project could continue with the corrected Student implementation.

---

## Final Evaluation

The GitHub Copilot review successfully identified a real syntax error and confirmed that the general structure of the Student class was correct.

The suggestion was reviewed manually before applying the change. This demonstrates that Copilot was used as a development assistant rather than as an automatic replacement for the programmer's judgment.
